# NextRole 관리자 가이드

**버전 1.1.0 · 한국어 · 2026-09-27**

NextRole은 Go API, React·TypeScript·Mantine 화면, PostgreSQL로 구성된 경력전환 시뮬레이터입니다. 웹 번들·아이콘·폰트를 서비스 이미지에 포함하며, 핵심 분석과 시뮬레이션은 인터넷 또는 외부 AI 없이 실행할 수 있습니다.

이 문서는 배포 담당자와 서비스 관리자를 위한 운영 가이드입니다. 화면은 실제 서비스에서 합성 데이터를 사용해 촬영했습니다. 별도의 라이브 공급자 인증정보 없이 외부 SSO나 고용24 실서비스 연결이 완료되었다는 의미는 아닙니다.

## 구성과 운영 범위

```text
사용자 브라우저
    │ HTTPS
조직의 리버스 프록시 / 내부 인증서
    │ HTTP :8080
NextRole 서비스 컨테이너
    ├─ Go API + React 정적 파일 + 한글 폰트 + PDF 추출기
    ├─ PostgreSQL (조직에서 별도 제공)
    ├─ 선택: 내부 OIDC / Keycloak
    ├─ 선택: 내부 OpenAI 호환 AI 서버
    └─ 선택: 승인된 HTTP API / PostgreSQL / MySQL 데이터 소스
```

릴리즈 첨부물은 **NextRole 서비스 Docker 이미지만** 압축한 `nextrole-v1.1.0.tar.gz`입니다. 이미지 태그는 `nextrole:v1.1.0`이며, PostgreSQL·AI 모델·Keycloak 이미지를 함께 넣지 않습니다. 필요한 기반 서비스는 조직의 반입·운영 절차에 따라 따로 준비합니다. 서비스 표시명은 `NextRole`, Docker 이름은 레지스트리 규칙에 맞춰 소문자 `nextrole`을 사용합니다.

소개 영상·한국어 자막·사용자/관리자 PDF·화면 캡처는 저장소의 `docs`와 GitHub Pages에서 제공합니다. 이 문서·영상 파일을 Docker 이미지 릴리즈 첨부물에 추가하지 않습니다.

### 오프라인 사용의 의미

네트워크가 차단되어도 로그인, 경력 입력·로컬 파싱, 직무 비교, 규칙 기반 시뮬레이션, 저장과 개인 키 관리는 동작합니다. 내부 서버에 연결할 수 있다면 사내 SSO·AI·데이터 연동도 사용할 수 있습니다.

Google·LinkedIn·카카오·네이버·고용24 같은 인터넷 서비스는 해당 서비스까지 연결되어야 사용할 수 있습니다. 폐쇄망에서 외부 데이터를 사용하려면 승인된 데이터 반입 후 내부 API·DB 또는 JSON 가져오기를 사용합니다. 기본 제공 데이터는 합성 모델이며 실제 고용24 원본을 내장한 것으로 해석하지 않습니다.

## 오프라인 배포

### 준비할 항목

- 이미지 아키텍처와 맞는 Docker 실행 호스트. 현재 배포 이미지는 릴리즈에 표기된 플랫폼을 확인합니다.
- 접근 가능한 PostgreSQL 15 이상과 NextRole 전용 데이터베이스·계정.
- 데이터베이스 스키마를 생성·변경할 권한. 서비스 시작 시 테이블을 준비합니다.
- 사용자 접속 URL과 운영 환경의 HTTPS 리버스 프록시.
- `nextrole-v1.1.0.tar.gz`, 저장소의 `compose.yaml`, `.env.example`.
- 안전하게 보관할 관리자 초기 비밀번호와 32바이트 암호화 키.

리버스 프록시와 데이터베이스는 서비스 컨테이너 외부에서 관리합니다. 대규모 배포에 대한 임의의 성능 수치는 제공하지 않으므로 실제 조직의 사용자·문서·모델 부하로 용량을 검증하세요.

### 환경변수 네 개

| 이름 | 내용 | 주의점 |
| --- | --- | --- |
| `POSTGRES_DSN` | 서비스 자체 데이터베이스 연결 문자열 | 비밀번호 URL 인코딩과 TLS 설정 확인 |
| `BOOTSTRAP_ADMIN` | 최초 관리자 이메일 | 최초 부트스트랩에 사용 |
| `BOOTSTRAP_ADMIN_PASSWORD` | 최초 관리자 비밀번호 | 12~72바이트의 충분히 긴 무작위 값 |
| `ENCRYPTION_KEY` | 무작위 32바이트를 base64 인코딩한 값 | DB의 암호화된 설정 복구에 반드시 필요 |

운영 AI 키, SSO Client ID·Secret, 연동 DB DSN 등은 추가 환경변수로 받지 않습니다. 로그인 후 **서비스 관리** 화면에 저장합니다.

```dotenv
POSTGRES_DSN=postgres://nextrole:REPLACE_DATABASE_PASSWORD@postgres.internal:5432/nextrole?sslmode=verify-full
BOOTSTRAP_ADMIN=admin@example.com
BOOTSTRAP_ADMIN_PASSWORD=REPLACE_WITH_LONG_RANDOM_PASSWORD
ENCRYPTION_KEY=REPLACE_WITH_32_BYTE_BASE64_KEY
```

위의 값은 형식 예시이며 그대로 사용하면 안 됩니다. 암호화 키는 다음 명령으로 생성해 비밀 저장소에 기록합니다.

```bash
openssl rand -base64 32
```

`ENCRYPTION_KEY`는 로그인 비밀번호나 개인 API 키와 다릅니다. 실행 때마다 새로 만들지 마세요. 기존 키를 바꾸면 DB에 저장된 AI·SSO·커넥터 비밀 설정을 복호화할 수 없습니다. 현재 버전은 이 마스터 키의 온라인 회전 도구를 제공하지 않습니다. 반면 개인 API 키는 사용자 화면에서 회전할 수 있습니다.

### 이미지 반입과 시작

신뢰하는 릴리즈에서 파일을 받아 조직의 무결성·반입 절차를 적용한 뒤 오프라인 호스트로 옮깁니다.

```bash
docker load --input nextrole-v1.1.0.tar.gz
docker image inspect nextrole:v1.1.0
cp .env.example .env
chmod 600 .env
```

`.env`의 네 값을 실제 환경에 맞게 편집한 다음 시작합니다.

```bash
docker compose up -d
docker compose ps
curl --fail http://127.0.0.1:8080/healthz
```

Compose는 로컬의 `nextrole:v1.1.0`을 사용하며 인터넷에서 자동으로 이미지를 가져오지 않습니다. 기본 서비스 포트는 8080입니다. `localhost`를 DB 주소로 쓰면 컨테이너 자신을 가리키므로, 컨테이너에서 도달 가능한 PostgreSQL 주소를 사용합니다.

서비스 프로세스는 비루트 사용자로 실행합니다. 제공한 Compose는 읽기 전용 루트 파일시스템, 문서 처리용 `/tmp` 임시 저장소와 제한된 컨테이너 권한을 사용합니다. DB 자료는 컨테이너 교체와 별도로 PostgreSQL에 보존됩니다.

### 시작 확인

1. `/healthz`가 `status: ok`와 버전을 반환하는지 확인합니다.
2. 로그인 화면에서 최초 관리자 이메일·비밀번호로 로그인합니다.
3. **서비스 관리 → 서비스 설정**에 실제 HTTPS 서비스 URL을 저장합니다.
4. **관리 대시보드**에서 PostgreSQL 연결, 버전, 사용자 수를 확인합니다.
5. **내 경력**에 합성 예시를 입력해 저장 → 시뮬레이션 → 결과 저장을 확인합니다.
6. 외부 인터넷 연결이 없는 상태에서 화면·폰트·로컬 계산이 동작하는지 확인합니다.

초기 관리자 환경변수는 기존 계정의 비밀번호 재설정 기능이 아닙니다. 초기 설정 후 비밀번호 변경은 **개인 설정** 또는 관리자의 **사용자 관리**에서 수행합니다. 로그인 복구를 환경변수 수정에 의존하지 말고 운영 계정 복구 절차를 마련하세요.

### 프록시와 스트리밍

공개·조직 서비스 URL은 관리자의 기본 URL과 일치시킵니다. API·웹 경로를 같은 출처에서 제공하세요. 프록시는 `/api/v1/ai/stream`의 응답을 버퍼링하지 않고 전달해야 합니다. AI가 긴 답변을 생성할 수 있으므로 프록시 응답 타임아웃도 모델 처리시간을 고려합니다.

SSE 응답에는 `Content-Type: text/event-stream`과 버퍼링 비활성 지시를 사용합니다. 화면에서 한 글자도 나오지 않다가 한꺼번에 출력된다면 AI 서버와 프록시 양쪽의 스트리밍 설정을 확인합니다. 단순한 로컬 시뮬레이션 API와 장시간 AI 스트림은 서로 다른 응답 특성을 가집니다.

## 관리자 공간

![관리 대시보드: 서비스 상태와 운영 메뉴](screenshots/admin.png)

왼쪽 **서비스 관리**로 이동하면 관리자 메뉴가 표시됩니다. **개인 공간으로**를 누르면 본인의 경력 공간으로 돌아갑니다. 단순히 메뉴를 숨기는 방식이 아니라 서버에서 관리자 역할을 검사합니다.

관리 대시보드에서 다음을 확인합니다.

- PostgreSQL 연결 상태와 현재 버전
- 전체 사용자·저장 시뮬레이션·데이터 연결 수
- 회원가입 허용 여부
- 검토·승인 기능 활성 여부
- AI 연결 또는 오프라인 엔진 사용 여부
- 합성 데이터 모드

## 사용자와 역할 관리

![사용자 관리: 계정, 역할과 활성 상태](screenshots/admin-users.png)

**사용자 추가**에서 이메일·이름·초기 비밀번호·역할을 지정합니다. 기존 계정은 **수정**으로 이름·역할·활성 상태를 바꾸고 필요한 경우 비밀번호를 재설정합니다.

| 역할 | 권한 |
| --- | --- |
| 사용자 `user` | 본인의 경력·결과·키·선호 관리 |
| 검토자 `reviewer` | 개인 기능과 검토 요청 승인·반려 |
| 서비스 관리자 `admin` | 관리 설정·사용자·데이터·감사, 검토 기능과 개인 기능 |

계정을 비활성화하면 로그인과 해당 계정의 API 키 사용이 제한됩니다. 역할 변경·비밀번호 재설정·비활성화 시 기존 로그인 세션이 만료될 수 있습니다. 개인 API 키 권한과 계정 역할은 다른 개념이며, 관리자 계정의 개인 키에도 관리자 API 권한을 부여하지 않습니다.

서비스를 관리할 계정이 남아 있어야 하므로 마지막 활성 관리자의 역할·상태 변경은 제한합니다. 한 사람의 실수로 운영 접근이 끊기지 않도록 관리자 계정을 적절히 관리하세요.

## 서비스 설정

![서비스 설정: 기본 URL, 회원가입, 합성 데이터와 검토 프로세스](screenshots/admin-general.png)

| 설정 | 동작 |
| --- | --- |
| 서비스 이름 | 공개 서비스 설정에 저장하는 표시 이름. 제품 브랜드는 NextRole |
| 서비스 외부 주소 | SSO 콜백과 사용자 접근에 사용하는 전체 기본 URL |
| 회원가입 허용 | 로그인 화면의 직접 가입 활성화. 기본 비활성 |
| 합성 데이터 모드 | 연동 결과가 없을 때 합성 교육·채용 예시 제공. 기본 활성 |
| 팀장 검토 · 승인 프로세스 | 검토 메뉴와 요청·승인·반려 API 활성화. 기본 비활성 |

v1.1.0부터 합성 데이터 모드를 끄면 내장 합성 직무와 합성 공고·훈련도 제외됩니다. 게시한 가공 직무나 별도 승인 직무가 없으면 목표 직무 목록은 비어 있습니다. 원천만 동기화했다고 시뮬레이션용 요구 수준이 자동 생성되지 않습니다.

회원가입 설정은 이메일·비밀번호 직접 가입을 제어합니다. SSO 공급자를 활성화하면 그 공급자에서 인증된 새로운 사용자의 최초 접근 계정이 만들어질 수 있으므로, 제한된 조직이라면 IdP 쪽 사용자·그룹 접근도 통제합니다.

### 검토 프로세스 운영

1. **사용자 관리**에서 검토 담당자를 `reviewer` 또는 `admin`으로 지정합니다.
2. **서비스 설정**에서 **팀장 검토 · 승인 프로세스**를 켜고 저장합니다.
3. 사용자가 저장된 시뮬레이션에서 검토를 요청합니다.
4. 검토자는 개인 공간의 **검토 · 승인**에서 의견과 함께 승인 또는 반려합니다.
5. 필요하지 않으면 기능을 끕니다. 메뉴가 사라지고 관련 API도 비활성화됩니다.

![선택적 검토·승인 화면](screenshots/approvals.png)

자기 요청 승인·반려는 허용하지 않습니다. 현재는 단일 검토 단계이며 팀 조직도·다단계 승인·팀장 자동 배정을 구현한 것이 아닙니다. 운영 역할을 배정해 필요한 검토 절차에 적용합니다.

## AI 모델 설정

![AI 설정: 서버, 모델, 스트리밍과 토큰 한도](screenshots/admin-ai.png)

기본값은 **AI 비활성**입니다. 핵심 경력 점수는 외부 LLM 응답에 의존하지 않습니다. AI를 사용하려면 OpenAI 호환 **Chat Completions 스트리밍** 엔드포인트를 제공하는 서버를 준비합니다.

### 설정 순서

1. **AI 모델 연결 사용**을 켭니다.
2. API 기본 주소에 모델 서버의 `/v1`까지 입력합니다. 예: `http://model.internal:8000/v1`.
3. 실제 서버가 제공하는 모델 이름을 입력합니다.
4. 인증이 필요하면 API 키를 입력합니다. 공란 수정은 기존 키를 유지합니다.
5. 출력 토큰 매개변수와 온도 사용 여부를 해당 서버·모델에 맞춥니다.
6. **최대 출력 토큰**과 **컨텍스트 윈도우**를 설정합니다.
7. **설정 저장** 후 **저장된 설정으로 연결 테스트**를 수행합니다.
8. 개인 공간에서 분석·설명 스트리밍을 실행해 실제 응답을 확인합니다.

### 출력 토큰과 컨텍스트는 다릅니다

| 항목 | 범위·의미 |
| --- | --- |
| 최대 출력 토큰 | 1~262,144. NextRole의 설정 상한이며 모든 모델이 이 출력을 지원한다는 뜻은 아님 |
| 컨텍스트 윈도우 | 1,024~2,097,152. 시스템 지시·입력·출력을 함께 담는 참고 한도 |
| 토큰 매개변수 | 호환 서버에 따라 `max_tokens` 또는 `max_completion_tokens` |
| Temperature | 전송하는 경우 0~2. 모델이 미지원하면 전송 비활성 |
| AI 요청 제한 시간 | 30~14,400초. 기본 3,600초이며 장시간 스트리밍과 프록시 제한을 함께 고려 |

최대 출력값은 컨텍스트보다 작거나 같아야 합니다. 실제 호출에서는 시스템 지시와 입력을 위한 공간도 필요하므로 둘을 똑같이 262,144로 놓으면 입력 여유가 없어 요청이 거절될 수 있습니다. 입력 예산은 모델별 토크나이저가 아닌 보수적인 바이트 추정으로 검사합니다. 모델 제공자의 실제 제한에 맞춰 여유를 둡니다.

기본 출력은 4,096, 컨텍스트는 262,144입니다. 256K 상한을 설정해도 서버의 메모리·시간·출력 한도는 별도로 제한될 수 있습니다. 로컬 모델의 KV 캐시와 동시 사용자 부하까지 고려해 검증하세요.

### 스트리밍·구조화 결과

AI 호출은 `stream: true`를 사용합니다. 클라이언트에는 SSE `delta`, 구조화 분석의 `profile`, 종료 `done`, 실패 `error` 이벤트가 전달됩니다. 사용자가 생성을 중지하거나 연결을 종료하면 요청 취소가 전달됩니다.

경력 파싱의 AI 결과는 JSON 형식과 범위를 검증하며 추출 역량을 `review`로 표시합니다. 사용자가 확인하지 않은 역량은 적합도에서 제외합니다. AI 설명에 공고·교육·급여·URL을 새로 만들지 않도록 지시하며 실제 기회 정보는 구조화된 연동 데이터에서 제공합니다. LLM이 생성한 설명은 모델 출력이므로 점수 근거와 대조하는 운영이 필요합니다.

AI 서버에 보내는 내용에는 경력 서술·프로필·시뮬레이션 근거가 포함될 수 있습니다. 폐쇄망 운영에서는 조직이 승인한 내부 AI 서버 주소를 사용합니다. 기본 주소의 `localhost`는 컨테이너 자신을 가리킵니다.

## 보안과 개인 키 정책

![보안·키 정책: 세션, 유효기간과 허용 범위](screenshots/admin-security.png)

| 설정 | 범위 | 기본값 |
| --- | ---: | ---: |
| 세션 유지 시간 | 1~168시간 | 12시간 |
| 개인 API 키 최대 유효기간 | 1~365일 | 90일 |
| 허용 범위 | 지원하는 권한 중 선택 | 지원 범위 전체 |

지원 범위는 `profile:read`, `profile:write`, `jobs:read`, `simulate:write`, `ai:use`, `mcp:use`입니다. 허용 목록을 줄이면 기존 키도 매 요청에서 새 정책의 제한을 받습니다. 최대 발급 기간을 바꾼다고 이미 만들어진 키의 만료일을 자동으로 소급 변경하지 않습니다.

개인 키는 소유자별로 관리하고 원문은 발급·회전 직후 한 번만 표시합니다. 서버에는 원문 대신 해시가 저장됩니다. 회전은 같은 키 기록의 인증 원문을 바꾸므로 구버전 키가 즉시 무효화되고 기존 만료일은 유지됩니다.

관리 설정의 민감한 값은 `ENCRYPTION_KEY`로 AES-GCM 암호화해 DB에 저장합니다. 사용자 비밀번호는 bcrypt, 세션과 API 토큰은 다이제스트 형태로 저장합니다. 관리 API에서 Client Secret·AI 키·연동 DSN의 원문을 다시 반환하지 않습니다.

서비스 설정의 비밀값 보호가 모든 DB 데이터를 암호화한다는 뜻은 아닙니다. 경력·시뮬레이션과 사용자 자료는 PostgreSQL 보안, 백업 암호화, 접근 권한과 디스크 암호화를 별도로 적용합니다.

## 점수 모델 관리

![점수 모델: 여섯 요소 가중치 편집](screenshots/admin-scoring.png)

가중치 합계는 100으로 설정합니다. 기본값은 기술역량 40, 전이 가능 역량 20, 경력 15, 산업경험 10, 교육·자격 5, 개인 선호 10입니다. 저장 후의 추천·재계산에 적용되며 이전 저장 결과를 자동으로 다시 쓰지 않습니다.

추천 정렬은 별도로 `적합도 + 선호 3점 + min(3, log2(관련 실제 공고 수 + 1))`의 보정을 사용합니다. 비선호 직무는 제외합니다. 이 보정은 정렬에만 사용하며 반환되는 여섯 요소 적합도 점수에는 합산하지 않습니다. 관련 실제 공고가 없으면 수요 보정은 0입니다.

### 계산 원리

- **기술역량**: 검증된 현재 수준을 요구 수준으로 나눈 값의 중요도 가중 평균.
- **전이 가능 역량**: 명시적인 로컬 특징 벡터의 코사인 유사도. 다른 기술의 유사도 기여는 최대 60%로 제한.
- **경력**: 입력 총 경력 / 참고 경력, 상한 적용. 목표 직무 관련성은 다른 요소에서 함께 확인.
- **산업경험**: 동일 산업은 일치, 정의된 인접 산업은 부분 일치, 미입력은 0.
- **교육·자격**: 학력 참고 요건 비교. 자격증별 검증 매핑이 없으면 이름만으로 가산하지 않음.
- **개인 선호**: 직무·분류 일치와 희망지역. 지역만 일치하면 요소의 절반까지.

별칭을 정규화하고 같은 역량 중복 입력은 점수를 중복 합산하지 않습니다. 추론·검증필요 항목은 확인 전 제외합니다. 로컬 특징 벡터는 외부 임베딩 모델이나 pgvector 서버가 필요 없는 결정적 의미 비교입니다. 현재 버전에 학습된 노동시장 예측 모델이나 실제 채용 성공 확률 모델이 포함되어 있다고 설명하지 마세요.

경력 공백은 `careerBreakMonths`(0~600개월)로 기록합니다. 공백 자체에 따른 점수 감점은 없으며, 최근 도구·업무 변화 점검과 복귀 프로젝트를 로드맵 첫 단계에 추가합니다.

난이도는 100에서 적합도를 뺀 값입니다. 계획 기간만 바꿔도 역량을 자동 취득한 것으로 보지 않으므로 점수는 동일합니다. 학습기간·비용은 합성 가정이며 실제 교육비와 구직기간은 따로 확인합니다.

## SSO 로그인 연동

![SSO 관리: 공급자 목록과 콜백 URI](screenshots/admin-providers.png)

Google·LinkedIn·카카오·네이버는 공급자 기본값을 사용하고, Keycloak·일반 OIDC는 발급자 메타데이터를 탐색합니다. 일반 OAuth 2.0은 인가·토큰·사용자정보 URL과 필드 매핑을 지정합니다.

### 공통 연결 순서

1. 공급자 콘솔에서 애플리케이션을 등록하고 Client ID·Secret을 준비합니다.
2. **서비스 설정 → 서비스 외부 주소**에 실제 서비스 URL을 저장합니다.
3. **SSO 로그인 연동 → SSO 연결 추가**에서 공급자 유형·이름·Client ID·Secret을 입력합니다.
4. 우선 비활성 상태로 저장해 고유 설정 ID와 **리디렉션 URI**를 확인합니다.
5. 공급자 콘솔에 화면에 표시된 URI를 정확히 등록합니다.
6. 필요한 동의 항목·테스트 사용자·앱 이용 권한을 설정합니다.
7. NextRole에서 연결을 활성화하고 로그인 화면의 버튼으로 실제 인증을 확인합니다.

콜백 형식은 다음과 같습니다. `{provider-id}`를 `google` 같은 공급자 유형 이름으로 임의로 바꾸지 말고 저장 후 화면에 나온 값을 사용합니다.

```text
https://nextrole.example.com/api/v1/auth/sso/{provider-id}/callback
```

Client Secret을 빈칸으로 수정하면 기존 값을 유지합니다. 값을 다시 보고 싶어도 원문은 반환되지 않습니다. 변경은 공급자에서 새 Secret을 발급한 뒤 NextRole에 덮어쓰는 방식으로 수행합니다.

### 공급자별 준비사항

| 제공자 | NextRole 기본값 | 공급자에서 확인할 항목 |
| --- | --- | --- |
| Google | OIDC, `openid profile email` | OAuth 클라이언트·동의 화면·정확한 리디렉션 URI |
| LinkedIn | OIDC, `openid profile email` | 앱의 Sign In with LinkedIn using OpenID Connect 제품 권한 |
| 카카오 | OIDC, `openid profile_nickname account_email` | 카카오 로그인 ON, OpenID Connect ON, REST API 키·Secret, 동의 항목 |
| 네이버 | OAuth 2.0, 사용자정보 `response.*` | 네이버 로그인 애플리케이션, Callback URL, 필요한 이용자 정보 |
| Keycloak | OIDC, 조직 Issuer 입력 | Client ID·Secret, Standard Flow, 콜백 URI, realm 사용자 접근 |
| 일반 OIDC | Issuer 메타데이터 자동 탐색 | discovery와 JWKS·토큰 엔드포인트 접근 |
| 일반 OAuth 2.0 | URL·필드 수동 지정 | 인가 코드 흐름과 사용자정보 고유 식별자 |

Google은 콘솔의 리디렉션 URI와 요청 URI가 정확히 일치해야 합니다. [Google OIDC 공식 문서](https://developers.google.com/identity/openid-connect/openid-connect)

LinkedIn 앱에 OIDC 로그인 제품 접근을 준비합니다. [LinkedIn OIDC 공식 문서](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/sign-in-with-linkedin-v2)

카카오의 현재 기본 설정은 ID 토큰을 사용하므로 OpenID Connect도 활성화해야 합니다. REST API 키의 Secret과 이메일 동의 범위를 확인합니다. [카카오 로그인 설정 공식 문서](https://developers.kakao.com/docs/ko/kakaologin/prerequisite)

네이버는 OIDC로 가정하지 않고 OAuth 인증 후 사용자정보 API의 `response.id`, `response.email`, `response.name`을 매핑합니다. [네이버 로그인 개발가이드](https://developers.naver.com/docs/login/devguide/devguide.md)

### Keycloak 오프라인 예시

Issuer 예시:

```text
https://sso.internal.example/realms/nextrole
```

`/.well-known/openid-configuration` 자체가 아니라 realm의 발급자 URL을 입력합니다. Keycloak의 discovery 경로는 해당 realm 아래에서 제공됩니다. [Keycloak OIDC 공식 문서](https://www.keycloak.org/securing-apps/oidc-layers)

Client 인증을 사용하는 웹 애플리케이션을 만들고 인가 코드 흐름과 필요한 scope를 설정합니다. 내부 DNS와 인증서 신뢰가 NextRole 서버·사용자 브라우저 모두에서 동작해야 합니다. 서버가 보는 Issuer와 ID 토큰의 Issuer가 다르면 검증이 실패합니다.

### 계정 식별과 제한

OIDC는 서명·Issuer·대상 클라이언트·만료·nonce를 검증하고, 인증 시작 상태는 한 번만 사용합니다. 공급자 설정이 로그인 도중 바뀌면 다시 로그인해야 합니다.

SSO 계정은 공급자 설정 ID와 고유 subject를 기준으로 식별합니다. 이메일이 같다는 이유만으로 기존 계정과 자동 연결하지 않습니다. 기존 사용자와 충돌하면 중복 안내가 나오며 기존 계정을 사용해야 합니다. 공급자를 삭제 후 새로 만들면 설정 ID가 달라지므로 기존 연결과 다른 공급자로 처리될 수 있습니다.

현재 버전은 조직 IdP 그룹을 관리자 역할로 자동 매핑하지 않습니다. SSO 신규 사용자는 일반 사용자이며 역할은 관리자가 변경합니다. NextRole 로그아웃은 서비스 세션을 종료하며 IdP의 전역 로그아웃을 대신하지 않습니다.

## 수집·분석 안내와 동의 관리

**개인정보 안내**에서 이용자에게 보여 줄 `notice`와 `version`을 저장합니다. 실제 수집 항목·목적, AI 서버 연결 조건, 경력 자료 삭제 범위와 조직의 보관 방침을 반영합니다. 안내 본문을 바꿀 때에는 새 버전을 지정해야 하며 기존 이용자는 다시 동의해야 합니다. 본문 해시도 확인하므로 과거 안내문에 한 동의를 새 안내문 동의로 처리하지 않습니다.

![개인정보 안내: 수집·이용 안내와 재동의 버전](screenshots/admin-data-policy.png)

이용자는 **개인정보·동의**에서 읽고 동의합니다. 동의하지 않아도 계정·키 관리와 권한이 있는 관리자 기능은 사용할 수 있습니다. 웹 경력 쓰기·분석·추천·교육채용 조회·시뮬레이션과 관련 MCP 호출은 현재 동의를 확인합니다. 관리자 계정도 본인 경력을 분석하려면 동의해야 합니다.

분석용 프로필은 이름을 보관하지 않습니다. 이메일·전화번호·주민등록번호, 이름·주소 등으로 표시된 줄을 정규식으로 제외하며, 입력한 프로필 이름이 있으면 해당 문자열도 제거합니다. 이력서 원본은 저장하지 않습니다. **이 처리는 완전한 익명화가 아니므로 이용자가 결과를 검토하도록 안내하세요.** 임의의 자연어에 있는 개인정보, 제3자 정보, 화면 캡처·기관 백업까지 자동 제거한다고 설명하지 않습니다.

철회하면 현재 동의와 해당 사용자의 `profile`, `simulation`, `roadmap`, `feedback`, 본인이 요청한 `approval`을 삭제합니다. 계정·API 키와 감사 로그는 유지됩니다. 동시 저장 요청이 철회 뒤 데이터를 다시 만들지 못하도록 동의 행 잠금으로 처리합니다. 조직 백업에 남은 이전 데이터의 관리·보관은 운영 정책에 따릅니다.

| MySQL 8 | 교육·채용 데이터 뷰 SELECT |
| JSON 가져오기 | 오프라인 반입 파일·직접 입력 |

`occupation_details`는 공공 직업상세 원천, `ncs_units`는 NCS 원천, `jobs`는 채용공고, `training`은 훈련 과정입니다. `occupations`는 별도로 검증한 사내 직무 사전을 위한 기존 형식입니다. 공공 원천을 `occupations`로 넣어 검토 절차를 우회하지 마세요. 공개 API 원천과 게시된 가공 모델은 별도로 보관합니다.

### 고용24 4종 프리셋

**데이터 연동**에서 직업상세 요약, 표준직무기술서, 채용정보, 국민내일배움카드 훈련 프리셋을 선택합니다. 요청 형식과 원천 구조를 적용한 다음 API 인증키·조회 조건·**저장할 원천 필드**를 지정합니다. 식별번호·제목·기관·원문 링크 등 프리셋별 필수 필드는 해제할 수 없습니다. 선택한 항목만 `raw`에 보관하며 API 전체 응답과 비밀키는 원문 레코드에 넣지 않습니다.

| 프리셋 | 관리자가 확인할 조건 |
| --- | --- |
| 직업정보 상세 · 요약 | 실제 `jobCd`; XML `jobSum` 객체, 그 안의 `jobSum`은 하는 일 |
| 표준직무기술서 · NCS | 관리자 입력 `jobCont`, `limit`; JSON `result`의 능력단위명별 객체 |
| 채용정보 | `startPage`, `display`, 필요 시 직종·지역·키워드; 최대 페이지 1000, 페이지 크기 100 |
| 국민내일배움카드 | `pageNum`, `pageSize`, `srchTraStDt`·`srchTraEndDt`; 두 날짜는 훈련 시작일 검색 범위 |

`jobCont`에는 개인 이력서를 자동 넣지 않습니다. 관리자가 승인한 수행직무 설명으로 조회합니다. 채용 목록에 요구기술 목록이 없으므로 제목에서 역량을 추론하여 저장하지 않습니다. 훈련 과정은 ID와 회차를 함께 보존하고 비용은 원문 문자열로만 참고합니다. 중단된 `eiEmplCnt3Gt10` 항목은 보관하지 않습니다.

[공식 전체 항목과 활용 목적](work24-data-plan.md), [프리셋 설정 예제](integrations.md)를 함께 확인하세요. 실제 승인 인증키는 개발 검증에 제공되지 않았으므로 운영 담당자가 연결 테스트·실제 동기화 결과를 확인해야 합니다.

### 일반 연결 구성 순서

1. **연결 추가**를 선택하고 이름·형식·용도를 지정합니다.
2. HTTP는 최종 URL, GET/POST, 인증키 전달 방식과 매개변수를 입력합니다.
3. DB는 별도의 읽기 전용 계정 DSN과 SELECT 조회를 입력합니다.
4. `rootPath`에 목록 경로를 지정합니다. 예: JSON `data.items`, XML `wantedRoot.wanted`.
5. 원본 필드를 NextRole 필드로 매핑합니다.
6. **연결 저장 → 연결 테스트**에서 변환된 레코드를 확인합니다.
7. 출처·고유 ID·제목·링크·역량·숫자 변환이 맞으면 **동기화**합니다.
8. 사용자 공간에서 실제 데이터와 출처 표시를 확인합니다.

HTTP 키가 query를 사용하는 경우 **인증키 쿼리 매개변수**에 `authKey` 등을 넣습니다. 키 원문은 **API 인증키**에 저장하며 URL·일반 매개변수·본문에 직접 넣지 않습니다. Bearer 헤더가 필요하면 인증키 값에 `Bearer 발급값`을 사용합니다.

테스트는 현재 설정의 한 페이지 또는 한 SQL 조회를 검사합니다. 동기화도 같은 범위이며 전체 페이지 자동 순회·정기 스케줄러는 포함하지 않습니다. 대량·정기 수집은 내부 게이트웨이에서 처리하거나 페이지 조건을 바꾸어 동기화합니다.

### 매핑 예제

원본이 `{"data":{"items":[{"code":"j1","name":"백엔드 개발자","company":"기관","tags":["Java"]}]}}`인 경우 목록 경로는 `data.items`입니다.

```json
{
  "id": "code",
  "title": "name",
  "organization": "company",
  "skills": "tags",
  "source.name": "=기관 채용 API",
  "source.synthetic": "=false"
}
```

상수는 `=`로 시작합니다. 배열의 값은 `tags[].label`처럼 매핑할 수 있습니다. 매핑을 지정하면 선택한 필드만 가져오므로 필요한 원문 URL과 출처도 포함하세요. 소스에 없는 공고·훈련 URL을 만들어 넣지 않습니다.

직무 역량은 문자열 목록이 아니라 `[{"name":"Python","level":4,"weight":1}]` 형식입니다. 기관의 NCS 수준과 NextRole 내부 수준(0~5)을 동일시하지 말고 담당자가 승인한 매핑을 사용합니다. 자세한 형식·고용24 실제 설정 예시는 [데이터 연동 상세 가이드](integrations.md)를 참고합니다.

### 조회 제한과 동기화 유의점

연동 어댑터는 HTTP 응답 10 MiB, 최대 5,000건, 연결 20초, SQL 실행 15초 등의 제한을 둡니다. XML 외부 엔티티·DTD, SQL 쓰기·다중문·위험 함수, HTTP 리디렉션은 허용하지 않습니다. 내부 URL에 접근하는 관리자 기능이므로 신뢰하는 운영자에게만 관리 권한을 부여합니다.

같은 원본 ID는 해당 출처의 기록을 갱신합니다. 연동 출처마다 ID를 구분해 충돌을 줄입니다. 커넥터 삭제는 연결 설정만 제거하고 이미 반입한 원천 레코드는 남깁니다. 원천 삭제는 **원천·가공 데이터**에서 별도로 수행합니다. 원본 시스템과 자동으로 양방향 삭제를 동기화하지 않습니다.

DB 정적 SQL 검사와 읽기 전용 트랜잭션은 실제 계정 권한을 대체하지 않습니다. 전용 계정에 승인된 뷰 SELECT만 부여하고 위험한 사용자 정의 함수·파일 접근 권한을 주지 않습니다.

### 실제 채용 시장 패널

사용자의 교육·채용 화면은 `/api/v1/market`의 실제 공고 집계를 함께 표시합니다. 지역별 기회, 요구 역량 변화와 공개 급여를 수집 데이터 범위 안에서 제공합니다. 기본 합성 공고는 집계하지 않으며, 과거 관측이 없으면 추세 비교를 표시하지 않습니다. 급여는 원본 표기를 보존합니다. 서로 다른 단위나 불완전한 표본으로 평균 연봉·시장 전체 수요를 만들어내지 않습니다.

유효 마감일 또는 상시채용 상태가 확인된 공고만 집계하며, 마감일 미제공·해석 불가 공고는 제외 건수로 안내합니다. 같은 URL은 중복 제거하고 지역은 원문의 구분값을 유지합니다. 직무별 관련성은 검토된 채용 직종코드, 정확한 제목 일치 또는 확인된 요구 역량 2개 이상의 일치로 판단합니다. 고용24 목록에는 요구기술이 없으므로 해당 API만 수집하면 역량 빈도·추세가 비어 있을 수 있습니다. 과거 버전에서 출처 없이 추론한 역량도 집계에서 제외합니다.

공고 수입 후 한국 시간 기준 일별 관측값을 저장합니다. 다른 날짜의 가장 최근 관측과 비교하며 `change`는 백분율이 아닌 공고 건수 차이입니다. 목표 직무명·요구역량이 바뀌면 비교 기준이 달라져 이전 관측을 사용하지 않습니다. 집계에 필요한 실제 공고와 안정적인 ID·역량·지역·원문·날짜를 매핑하고 수집 범위를 운영자가 기록하세요. 공고 수가 작거나 수집 페이지가 달라진 경우 이를 실제 노동시장 변화와 동일하게 해석하지 않습니다. 자세한 산식과 스키마는 [채용 시장 데이터 가이드](market-data.md)를 참고하세요.

### JSON 직접 가져오기

**JSON 가져오기**에서 데이터 용도와 레코드 배열을 입력하거나 `.json` 파일을 선택합니다. 관리자가 승인한 원본 출처를 기록하세요. 간단한 직무 레코드 예시는 다음과 같습니다.

```json
[
  {
    "id": "internal-platform",
    "title": "사내 플랫폼 엔지니어",
    "category": "개발·인프라",
    "description": "기관에서 검증한 직무 정의",
    "skills": [
      {"name":"Go","level":4,"weight":1},
      {"name":"Linux","level":3,"weight":1}
    ],
    "minExperience": 3,
    "domain": "IT",
    "education": "무관",
    "regions": ["서울"],
    "bridgeIds": [],
    "source": {"name":"사내 승인 직무 사전","url":"","synthetic":false}
  }
]
```

운영 JSON에는 실제로 검증한 자료만 사용합니다. 단지 파일을 가져왔다는 사실이 원본 데이터의 사실성이나 이용 허가를 증명하는 것은 아닙니다.

## 원천 데이터 관리

**원천·가공 데이터**에서 데이터 종류·출처별 건수, 수집 시각과 목록을 확인합니다. 종류를 고르고 제목·ID·기관으로 검색한 뒤 원천 필드를 펼쳐 확인합니다. 관리자가 보는 원천 목록은 공용 반입 자료이며 개인 경력 자료를 포함하지 않습니다.

![원천·가공 데이터: 출처·선택 원문 조회와 관리](screenshots/admin-data.png)

`source.kind`, 제공기관(`provider`), API 종류(`dataset`), 공식 출처 URL, 원천 ID(`recordId`), 수집 시각(`retrievedAt`)과 선택 필드(`fields`)를 점검합니다. 내부 레코드 ID는 `커넥터ID:원천ID`처럼 출처를 포함하므로 같은 원천번호가 여러 연동에 있어도 구분됩니다. 필요한 레코드만 삭제할 수 있으며 해당 자료를 참조하는 가공 직무는 다시 유효해질 때까지 계산에서 제외됩니다.

## 직무·역량 매핑 검토와 게시

**역량 매핑 검토**은 공공 원천의 문장을 내부 계산 모델로 해석한 별도 가공 자료입니다. 공식 원문에는 NextRole의 0~5 요구 수준과 가중치가 없습니다. 이 값을 자동 생성하지 않고 관리자가 근거를 기록하고 게시합니다.

![역량 매핑 검토: 근거·내부 기준·게시 버전 관리](screenshots/admin-mappings.png)

1. **원천·가공 데이터**에서 직업상세 원문을 확인하고 사용할 NCS 능력단위를 고릅니다.
2. 새 매핑의 직무명·원천 직무 레코드·선택 NCS 원천·전체 매핑 근거를 입력합니다.
3. 각 역량에 내부 ID·이름·별칭·내부 요구 수준(0 초과~5)·가중치(0 초과~100)·참조 원천 ID·판단 근거를 입력합니다. 별칭은 해당 내부 직무에서만 같은 역량으로 비교하며 NCS 공식 동등성을 의미하지 않습니다.
4. 채용 연결이 필요하면 **연결할 채용 직종코드**를 별도로 검토해 입력합니다. 직업상세의 `jobCd`와 공고의 `jobsCd`가 같다고 가정하거나 코드 접두어로 추정하지 않습니다.
5. **검토 전 초안 저장** 후 원문과 설정값을 검토하고 현재 버전을 **검토 후 게시**하고 확인 항목에 체크한 뒤 **검토 완료 및 버전 게시**합니다. 초안·삭제된 매핑·원천이 없는 매핑은 시뮬레이션에 들어가지 않습니다.
6. 사용자 공간에서 가공 출처·버전·요구 수준·점수 이유와 연결 과정을 확인합니다.

저장·게시·삭제마다 버전 이력을 남깁니다. 수정하면 다시 초안이 되어 기존 게시 직무가 계산에서 빠지며 재게시가 필요합니다. 오래된 버전으로 수정·게시하면 충돌(409)을 반환하므로 최신 내용을 불러와 검토합니다. 삭제 후에도 매핑 이력은 남습니다.

게시 시 참조 원천의 내용 지문을 기록합니다. 같은 내용의 재수집은 게시 상태를 유지하지만 원문 내용 변경·삭제는 유효성을 잃게 하여 다시 검토·게시해야 합니다. 상태가 게시여도 유효성 경고가 있으면 계산에 사용하지 않습니다.

훈련 연결은 게시한 NCS 원천의 코드, 특히 `job_sdvn_cd` 세분류코드를 원천 훈련의 `ncsCd`와 정확히 비교합니다. 해당 필드를 수집에서 제외하면 없는 코드를 추정하지 않습니다. 훈련 제목에서 기술을 생성하거나 능력단위 코드 일부를 잘라 같은 코드라고 단정하지 않습니다.

요구 경력·학력 기준이 없는 공공 가공 모델은 해당 요소를 임의로 충족 처리하지 않습니다. 0점과 그 이유를 표시하며 누락 배점을 다른 요소에 재분배하지 않습니다. 점수 비교 시 데이터 완성도와 근거를 함께 확인합니다.

## REST API와 MCP 운영

![API·MCP 연결 안내 화면](screenshots/api.png)

API 명세는 `/api/v1/openapi.json`에서 확인합니다. 사용자 데이터 API는 Bearer 키 범위와 소유자를 검사합니다. 관리자 API는 관리자 로그인 세션으로만 접근하며 개인 키로 관리자 작업을 수행하지 않습니다.

MCP 엔드포인트는 `/mcp`와 `/api/v1/mcp`입니다. HTTP POST JSON-RPC로 `initialize`, `ping`, `tools/list`, `tools/call`과 알림을 지원합니다. 클라이언트별 원격 HTTP·Bearer 헤더 지원 여부를 확인하세요. 브라우저 쿠키를 외부 AI 도구에 전달하지 말고 전용 개인 키를 사용합니다.

| 도구 | 필요한 범위 |
| --- | --- |
| `career_profile` | `mcp:use` + `profile:read` |
| `job_search` | `mcp:use` + `jobs:read` |
| `career_simulate` | `mcp:use` + `simulate:write` |
| `career_opportunities` | `mcp:use` + `jobs:read` |

도구 목록은 권한에 맞춰 반환하며 호출 때도 다시 검사합니다. MCP 시뮬레이션은 프로필을 변경하거나 계산 결과를 저장하지 않습니다. REST의 저장 옵션은 별도입니다.

경력 작업 전에 `GET /api/v1/privacy`로 안내·버전을 조회하고 본인이 확인한 뒤 `POST /api/v1/privacy/consent`로 명시 동의합니다. `DELETE /api/v1/privacy/consent`는 철회와 개인 경력 자료 삭제를 수행합니다. 개인정보 안내를 대신 읽었다고 가정하는 자동 동의 코드를 배포하지 마세요. MCP의 경력 시뮬레이션·기회 조회 도구도 같은 계정의 현재 동의를 확인하며, 공공 직무 검색과 계정 기능의 권한은 별도로 적용합니다.

관리자 API는 `/admin/connector-presets`, `/admin/data`, `/admin/source-records`, `/admin/mappings`, `/admin/mappings/{id}/history`, `/admin/mappings/{id}/publish`, `/admin/data-policy`를 제공합니다. 개인 API 키로 관리자 권한을 우회하지 않습니다. 요청·응답 계약은 [구현 계약](architecture.md)을 참고합니다.

## 감사 로그와 상태 확인

![감사 로그: 작업자, 작업, 대상과 일시](screenshots/admin-audit.png)

**감사 로그**에서 로그인, 관리자 설정, 사용자 역할, SSO·커넥터, 키 관리와 AI 관련 주요 작업을 조회합니다. 검색창으로 작업자·작업·대상을 좁힐 수 있습니다. 감사 로그가 모든 페이지 조회와 외부 시스템의 세부 응답을 기록하는 것은 아닙니다.

민감한 원격 오류 본문이나 인증키를 화면에 그대로 표시하지 않습니다. 기본 로그 보존과 보관 정책은 조직 PostgreSQL·로그 시스템에서 별도로 운영하세요. 서비스 로그는 다음 명령으로 확인할 수 있습니다.

```bash
docker compose logs --tail=200 nextrole
```

서비스 상태는 `/healthz`, 관리자 상세 상태는 `/api/v1/admin/status`에서 확인합니다. 공개 헬스 응답에는 민감한 계정 수·연동 정보가 포함되지 않습니다.

## 백업·복구·업그레이드

### 백업 범위

다음을 서로 안전하게 관리합니다.

1. PostgreSQL의 NextRole 데이터 전체: 사용자·프로필·설정·저장 결과·연동 데이터·감사 기록.
2. 원본 `ENCRYPTION_KEY`: DB 암호화 설정 복호화에 필요.
3. 운영 `.env`, Compose, 프록시·TLS 구성의 안전한 사본.
4. 현재 사용한 서비스 이미지와 정확한 버전.

PostgreSQL 백업에는 경력 등 개인정보가 포함되므로 접근과 암호화를 적용합니다. 데이터베이스 덤프와 암호화 키를 함께 노출하지 않습니다. 다음은 DB 담당자가 사용 가능한 PostgreSQL 도구에서 수행하는 예시이며 암호는 비밀 저장소 또는 `.pgpass` 등으로 공급합니다.

```bash
pg_dump --host=postgres.internal --username=nextrole \
  --dbname=nextrole --format=custom --file=nextrole-backup.dump
```

복구는 운영 DB를 즉시 덮어쓰기 전에 별도 복구 DB에서 먼저 검증합니다. 동일 버전 이미지와 **원래 암호화 키**로 로그인, 설정 조회, 저장 결과를 확인한 뒤 운영 전환합니다. 백업 파일만 있고 암호화 키가 없으면 비밀 설정은 복구할 수 없습니다.

### 업그레이드 순서

1. 릴리즈 변경 내용과 대상 플랫폼을 확인합니다.
2. 현재 DB·암호화 키·운영 설정을 백업합니다.
3. 새 `nextrole-v버전.tar.gz`를 반입하고 `docker load`합니다.
4. 별도 환경에서 기존 DB 사본과 새 이미지의 호환성을 점검합니다.
5. Compose 이미지 태그를 정확한 `nextrole:v버전`으로 바꿉니다.
6. 유지보수 시간에 `docker compose up -d`를 실행합니다.
7. 헬스, 로그인, 프로필, 시뮬레이션, 연결·키·SSO를 확인합니다.

DB 스키마가 바뀐 릴리즈의 롤백은 이미지 태그만 되돌려서 안전하다고 가정하지 않습니다. 검증한 이미지·DB·설정 조합으로 복구합니다. `latest` 태그에 의존하지 않고 명시적 버전을 사용합니다.

## 운영 문제 해결

| 증상 | 점검 순서 |
| --- | --- |
| 시작 시 환경변수 오류 | 네 값 존재, 비밀번호 12~72바이트, base64 디코딩 후 32바이트 키 |
| PostgreSQL 연결 실패 | 컨테이너 DNS·경로·방화벽, DSN 인코딩, 계정, TLS 인증서 |
| 설정 복호화 실패 | DB를 만들 때 사용한 원래 ENCRYPTION_KEY인지 확인 |
| 로그인 성공 후 API 오류 | 동일 출처 URL, 프록시 Host·HTTPS, 세션 만료 |
| 새로고침 시 404 | 프록시가 하위 경로를 NextRole로 전달하는지 확인 |
| SSO 메타데이터 실패 | Issuer, DNS·TLS, discovery 접근, IdP 상태 |
| SSO callback mismatch | 저장된 기본 URL, 실제 provider ID, 콘솔 URI 정확 일치 |
| SSO ID 토큰 없음 | 공급자 OIDC 활성과 openid scope |
| AI 연결 테스트 실패 | 설정 저장, `/v1` 주소, 모델명·키, streaming 지원 |
| AI context 예산 초과 | 출력 상한을 줄여 입력 공간 확보, 실제 모델 컨텍스트 확인 |
| AI가 한꺼번에 출력 | 프록시 버퍼링, 서버 Content-Type과 SSE 형식 |
| 커넥터 301/302 | 리디렉션 이후 최종 주소를 직접 등록 |
| 데이터 목록 없음 | 실제 오류 응답, rootPath, 필드 선택, 지역·검토 코드 매핑, 출처와 수집 범위 |
| 직무 목록이 비어 있음 | 합성 모드와 유효한 게시 매핑 여부. 공공 원문 동기화만으로 계산 직무가 생성되지 않음 |
| 매핑 게시 뒤 직무가 사라짐 | 원천 수정·삭제, 매핑을 초안으로 수정했는지, 유효성 경고 |
| 경력 API에서 동의 필요 | 현재 안내 버전·본문과 이용자 동의 일치 여부 |
| 실제 공고는 있지만 역량 추세 없음 | 고용24 목록엔 요구기술 없음. 출처 있는 요구기술 자료·이전 v2 스냅샷 여부 |
| SQL 테스트 실패 | 읽기 전용 계정, SELECT 문법, 뷰·함수 권한과 실행시간 |
| API 키가 403 | 키 범위와 현재 서비스 허용 범위 둘 다 점검 |
| 검토 메뉴 없음 | approvalEnabled 활성 여부와 사용자 역할 |
| PDF 추출 실패 | 텍스트 PDF 여부, 암호화, 크기·페이지, 내장 pdftotext |

## 운영 인수인계 체크

- 서비스와 릴리즈 버전, 이미지 태그·플랫폼을 기록했습니다.
- 네 환경변수와 암호화 키 복구 위치를 확인했습니다.
- PostgreSQL 백업·복구를 별도 환경에서 실제 수행했습니다.
- 로컬 관리자 로그인과 필요한 SSO 공급자의 실제 로그인을 검증했습니다.
- 합성 예시와 운영 데이터를 구분하고 담당자가 출처를 검증했습니다.
- AI를 켰다면 모델별 토큰·컨텍스트·스트리밍 제한을 검증했습니다.
- 키 회전 후 이전 키가 거절되고 새 키가 동작하는지 확인했습니다.
- 검토 절차를 쓰지 않으면 비활성 상태임을 확인했습니다.
- 모바일과 하위 메뉴 새로고침, 저장 후 재접속을 확인했습니다.
- 사용자에게 적합도가 취업 확률이 아니라는 안내를 전달했습니다.

외부 공급자의 콘솔·정책은 변경될 수 있습니다. 위 링크의 공식 문서와 현재 조직의 계약·네트워크 조건을 함께 확인하세요.
